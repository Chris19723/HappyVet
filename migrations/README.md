# HA-FOUND-001 — Versioned migrations

This replaces `drizzle-kit push` as the change-management path for high-risk
tenant/clinical structural changes. Migrations are plain SQL files applied in
filename order by a transactional, tracked runner (`scripts/migrate.ts`,
tracking table `_ha_migrations`).

## Files
- `0000_baseline.sql` — current pre-tenant schema (generated by `drizzle-kit generate`).
- `0001_tenant_expand.sql` — EXPAND: create tenant tables + add NULLABLE tenant
  columns + composite/triple UNIQUE keys + the Membership↔StaffMember identity
  FK. Safe on populated tables. Invoice numbers stay GLOBALLY unique.
- `0002_tenant_enforce.sql` — ENFORCE: `NOT NULL` (incl. medical_records.branch_id)
  + simple/composite/branch-aware FKs. Run only AFTER backfill. No per-org
  invoice-number constraint (global uniqueness is preserved).

## Baseline adoption (legacy databases)
`db:migrate` inspects the database before applying anything:
- fresh DB → `0000_baseline.sql` is applied normally;
- an existing legacy schema that matches the baseline (all expected tables +
  key columns) → `0000` is RECORDED as adopted WITHOUT running its SQL;
- a partial/unknown legacy schema → the runner ABORTS (fail closed).

## Safe process (development / staging — NEVER production without HQ authorization)

```bash
# 1. GENERATE (future schema diffs)
npm run db:generate            # drizzle-kit generate from shared/schema.ts

# 2. REVIEW
#    Read the generated/hand-authored SQL. Confirm expand-only vs enforce.

# 3. TEST APPLY (fresh disposable DB)
export DATABASE_URL=postgres://…/throwaway
npm run db:migrate             # applies all pending, each in its own tx
npm run db:migrate:status      # shows APPLIED / PENDING

# 4. LEGACY CUTOVER (data present) — adopt/expand → bootstrap → backfill → users → enforce
npm run db:migrate -- --to 0001_tenant_expand   # adopts baseline (legacy) then EXPAND
ORG_NAME="<real>" BRANCH_NAME="<real>" [ADMIN_USER_ID=<id> ADMIN_ROLE=admin] npm run tenant:bootstrap
BACKFILL_ORG_ID=<id> BACKFILL_BRANCH_ID=<id> npm run tenant:backfill   # prints reconciliation
USER_MANIFEST=<path.json> npm run tenant:migrate-users   # approved users only, fail closed
npm run db:migrate             # applies 0002 enforce

# 5. VERIFY
#    - backfill output: remainingNulls all 0 (medical_records.branch_id now REQUIRED → must be 0)
#    - migrate-users: apptsLegacyVetUnmapped / recordsLegacyVetUnmapped == 0
#    - reconciliation before/after: identical counts + sums (ZERO delta)
npm run tenant:preflight       # read-only user classification (creates nothing)
```

## Rollback / recovery
- Each migration runs in its own transaction; a failure leaves the DB on the
  last fully-applied migration (restartable).
- The backfill only UPDATEs NULL columns, so it is idempotent/restartable.
- ENFORCE is the point of no easy return; take a database backup before it.
- Full inverse-DDL down-migrations are not included in this task (EXPAND is
  additive and reversible by dropping the new columns/tables/constraints).

## Bootstrap rule
`tenant:bootstrap` refuses to run without explicit `ORG_NAME` and `BRANCH_NAME`.
It never invents tenant identity, defaults the first membership to `admin`
(never `owner`), and is idempotent by name (safe to re-run — no duplicate tenant).

## User migration rule
`tenant:migrate-users` is manifest-driven: it maps ONLY the approved users listed
in the manifest, uses their explicit `staffDisplayName` verbatim, and ABORTS if any
legacy `veterinarian_id` in the org's data is missing from the manifest (fail closed).
